# dsh 插件发布流程手册（通用脱敏版）

> 每次发布（git + npm 整体更新）必须按本手册执行。
> 本文件为**公开脱敏版**，不含本机路径。配套技能：`dsh-release`、`dsh-troubleshoot`。

---

## 〇、发布前置：明确本次改动类型（决定版本号）

| 改动类型 | 版本号规则（SemVer） | 示例 |
|---|---|---|
| Bug 修复（向后兼容） | 修订号 +1 | 0.2.0 → 0.2.1 |
| 新功能（向后兼容） | 次版本 +1 | 0.1.1 → 0.2.0 |
| 破坏性变更 | 主版本 +1（0.x 阶段慎重） | 1.0.0 → 2.0.0 |
| 首次发布 | 从 0.1.0 起 | — |

---

## 一、代码检查（改代码后、发布前必做）

- [ ] **语法检查**：`node --check lib/index.js` + `node --check lib/client.js`（两个都要，exit=0）
- [ ] **旧名残留扫描**（涉及改名时）：grep 插件目录全部文件（`.yml`/`.js`/`.json`/`.md`），确认无旧包名
- [ ] **三层同步检查**（作用域包改名后）：

| 层 | 文件 | 字段 | 必须是 |
|---|---|---|---|
| 依赖声明 | `package.json` | `name` | 完整包名 `@<作者>/<包>` |
| 服务端挂载 | `cordis.patch.yml` | `name` | 完整包名 |
| 客户端模块 | `lib/client.js` | `__ModuleLoader__.load({ id })` | 完整包名 |

> 代码内注册名（`export const name`、slots id、API 路由）可保留短名，参照 modlens 模式。
> ⚠️ 这三处是崩溃事故的根因，**漏一处 = 启动失败**。

- [ ] **三处一致性**：git 仓库 / npm 已发布包 / 本地安装目录，代码哈希一致

---

## 二、版本检查（发布前必做）

- [ ] 确认 npm 上当前 latest 版本：`npm view <包> version`
- [ ] 确认本地 `package.json` 的 `version` **高于**线上版本（不能等于，npm 拒绝重复发布）
- [ ] 修改版本号：手动改 `package.json`，或 `npm version patch/minor`（自动改 + 打 tag）
- [ ] 确认 `CHANGELOG.md` 已加对应版本条目

### CHANGELOG 格式

```markdown
## [X.Y.Z] - YYYY-MM-DD

### Added      # 新功能
### Fixed      # Bug 修复（写清根因和修复方式）
### Changed    # 行为/结构变更
```

---

## 三、内容检查（文档/README 必做）

- [ ] 插件 README：版本号、安装命令（`npm install @<作者>/<包>`）、功能说明是否最新
- [ ] 仓库根 README：插件列表表格的版本号、说明
- [ ] 无"写给特定环境/待办"的话：如 `（当前环境）`、`（发布后）`、`（规划中）` 等
- [ ] 无过时描述（功能变了但文档没改）
- [ ] npm 包内容确认：`npm pack --dry-run` 检查文件清单

---

## 四、隐私检查（公开仓库必做，重点！）

- [ ] 对**每个要发布的文件**扫描以下模式（grep）：
  - 盘符路径、用户目录、用户名
  - token：`ghp_`（GitHub）、`npm_`（npm）、API key
  - 数据目录、个人项目名
- [ ] 含本机信息的文档**只存本地**，仓库里放**脱敏版**
- [ ] README/CHANGELOG/SKILL.md 用占位符：`<安装目录>`、`$DSH_HOME`、`<作者>`

---

## 五、安全检查（避免被黑客利用）

- [ ] **token 不写入任何公开文件**（.npmrc 里的 token 不提交；remote URL 不带 token）
- [ ] **token 不外泄**：不在对话中明文贴完整 token；必要时用完吊销重新生成
- [ ] 插件**不含硬编码密钥**（API key 走环境变量/配置文件，不进代码）
- [ ] **API key 永不备份/还原**：确认 `.credentials.yaml` 等密钥文件在 NEVER 集合中
- [ ] 插件 API 仅 loopback（127.0.0.1）响应
- [ ] 后台操作全部 try-catch，失败只记日志不影响主进程
- [ ] npm 包依赖零外部包（减少供应链风险）

---

## 六、本地验证（发布前必做）

- [ ] **API 实测**（dsh 运行中）：
  - `GET /dsh-backup/status` → 200 ok=true
  - `GET /dsh-backup/config` → 200
- [ ] **备份实测**：POST `/dsh-backup/backup {type:'incremental'}` → 检查 manifest 的 `plugins`/`skills`
- [ ] **配置解析**（可选）：`dsh --profile web --dump-config` 确认插件挂载正常
- [ ] 若改动涉及服务端/客户端加载：**告知用户重启 dsh**（不自行杀/启进程），重启后复测

---

## 七、发布顺序（严格按此顺序，不可跳步）

### 第 1 步：git 提交并推送
```bash
git add -A
git commit -m "type(scope): description"   # 如 "release: v0.2.1 - fix ..."
git push
```
> 先推代码，再发 npm。若推送网络失败（SSL），检查 VPN/代理后重试。

### 第 2 步：npm 发布
```bash
npm publish --access public
```
> 作用域包**必须** `--access public`（否则 E402）。

### 第 3 步：线上验证
- [ ] `npm view <包> version` → 等于刚发布的版本
- [ ] **不要因 `npm view` 404 慌**：CDN 传播延迟几分钟内恢复。用以下确认：
  - 重复 `npm publish` 报 `403 You cannot publish over the previously published versions` = **已成功**
  - 或 jsDelivr：`curl https://cdn.jsdelivr.net/npm/<包>@<版本>/package.json` → HTTP 200
- [ ] `npm pack <包>@<版本>` 检查 tarball 内容正确

---

## 八、发布后收尾

- [ ] 本地安装目录更新到新版本（如需立即使用）
- [ ] 若涉及新坑：**把事故写入经验库**和 `dsh-troubleshoot` 技能
- [ ] 确认 git 状态干净（无未推送提交）

---

## 九、网络问题排查（VPN/代理）

| 症状 | 原因 | 处理 |
|---|---|---|
| `schannel: failed to receive handshake, SSL/TLS connection failed` | VPN/代理与 schannel 冲突 | 检查代理端口（如 7897）；`git config --global http.proxy http://127.0.0.1:7897`；或切换 VPN 模式 |
| github.com 直连失败 | 网络/VPN 未生效 | 测试代理连通性；确认 VPN 已连接 |

---

## 快速检查口诀（发布前默念）
