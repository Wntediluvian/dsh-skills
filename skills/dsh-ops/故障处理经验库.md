# dsh 故障处理经验库（通用脱敏版）

> 本文件是 dsh 故障经验的**公开脱敏版**，不含任何本机路径/用户名/token。
> 供 dsh-ops 技能引用。含个人细节的完整版仅保存在使用者本地。
> **每次处理完重大错误后，应同步更新本档案与本地完整版。**

---

## 事故 0：dsh 崩溃 —— zstd 会话文件被错误合并成单帧

**根因类型**：⚠️ **数据文件格式被破坏**

### 症状

- dsh 无法启动，报 `corrupt Zstandard session log: first frame is not exactly one header line`

### 根因（关键知识点）

- dsh 会话文件（`session.jsonl.zstd`）是 **zstd 多帧 JSONL**：每个 JSON 对象一个独立 zstd 帧
- **第一帧必须是恰好一行 header**（`assertZstdHeaderFrame` 校验）
- 用"整体解压 → 整体压缩"会合并成单帧 = **损坏**
- 正确修复：**逐帧处理**，保留帧边界

### 预防

- [ ] **绝不**用整体解压/整体压缩改写 dsh 会话文件
- [ ] 处理 zstd 会话必须逐帧操作
- [ ] 改 dsh 数据前先备份

## 事故 1：插件包名从裸名改为作用域包后漏改 3 处引用

**根因类型**：⚠️ **改名/改结构时旧名残留**（最高频事故类型）

### 症状

- 启动报 `Cannot find package '<旧包名>'`（服务端）
- 浏览器报 `loaded without registering "@<新包名>"`（客户端）

### 根因（关键知识点）

包名是**三层系统**，改名时三层都要同步：

| 层 | 文件 | 字段 | 作用 |
|---|---|---|---|
| ① 依赖声明 | `package.json` | `name` | npm 包身份 |
| ② 服务端挂载 | `cordis.patch.yml` | `name` | loader 按**包名** import |
| ③ 客户端模块 | `lib/client.js` | `__ModuleLoader__.load({ id })` | 浏览器端注册名 |

**可保留短名的地方**（对照 modlens 官方模式）：
- `lib/index.js` 的 `export const name`（cordis 注册 id）
- slots 注册的 `id`（界面条目 id）
- HTTP 路由前缀

### 预防

- [ ] 改名后全局搜索旧包名（含 `.yml` 和 `.js`）
- [ ] 对照 modlens：**patch name / client id = 完整包名，代码内注册名 = 短名**

## 事故 2：npm 发布后 registry 查询 404（CDN 传播延迟）

**症状**：发布命令成功但 `npm view` / registry API 404
**根因**：npm registry 的**写入节点与读取节点（CDN 边缘）传播有延迟**

### 判断发布是否成功（三连验证）

1. **重复发布**：再跑 `npm publish --access public` → 报 `You cannot publish over the previously published versions: X.Y.Z` = **包确实已发布**
2. **jsDelivr 交叉验证**：`https://cdn.jsdelivr.net/npm/<包>@<版本>/package.json` → HTTP 200
3. **等待后重查**：`npm view` 通常几分钟内恢复

### 预防

- [ ] 发布后不要立刻用 `npm view` 判断成败
- [ ] 发布命令 exit=0 + 无报错 = 已成功

## 事故 3：npm 发布 E402 / E403（作用域包访问权限）

| 报错 | 原因 | 修复 |
|---|---|---|
| `402 ... private packages` | 作用域包默认按**私有包**处理 | `npm publish --access public` |
| `403 ... bypass 2fa enabled` | npm 新政策：发布必须 2FA 或 bypass-2FA token | 生成 Granular Access Token 并勾选 **Bypass 2FA** |

## 事故 4：npm EOTP（一次性验证码）

**症状**：`npm publish` 报 `EOTP: This operation requires a one-time password`
**修复**：`npm publish --otp=<手机 Authenticator 的 6 位动态码>`（30 秒内有效）
**注意**：动态码是 Authenticator 生成的 TOTP，**不是**解锁系统的 PIN。

## 事故 6：隐私保护 —— 含本机信息的文件绝不发布到公开仓库

**根因**：开发期文档天然包含本机细节（绝对路径、用户目录、token、数据目录），直接复制进公开仓库即泄露

### 铁律

> **发布到公开仓库（GitHub/npm）的任何文件，绝不包含：本机路径、用户名、token、API key、数据目录结构。**

### 判断标准（发布前扫描）

| 模式 | 示例 | 处理 |
|---|---|---|
| 盘符绝对路径 | `D:\Program Files\...` | 占位符 `<安装目录>` 或删掉 |
| 用户目录 | `C:\Users\<用户名>\...` | 改为 `~` 或删除 |
| token | `ghp_xxx` / `npm_xxx` | 绝不出现（用 `<token>` 代替） |
| 数据目录 | `...\dsh-data\profiles\...` | 用 `$DSH_HOME/...` 表示 |

### 正确做法（双文件模式）

| 文件 | 用途 | 内容 |
|---|---|---|
| **本地完整版** | 自己看，含全部路径细节 | 完整保留 |
| **发布公开版** | 给别人看，零隐私 | 路径用占位符，规则通用化 |

### 编码陷阱

用 PowerShell `Set-Content -Encoding UTF8` 写中文文件会得到 **UTF-8 with BOM 且内容被 GBK 误解**，导致技能解析失败（乱码）。写中文文件必须用 write 工具（正确 UTF-8 无 BOM）。

## 事故 7：GitHub token 泄露 —— token 曾写入 remote URL

**根因类型**：⚠️ **凭据泄露**

### 根因

早期推送时把 token 拼进 remote URL（`https://user:token@github.com/...`）绕开认证。该 URL 会被 git 记录、也可能被日志/截图泄露。

### 铁律

> **token 绝不写入 git remote URL、绝不写进代码/配置文件、绝不在对话中明文贴出。**
> 认证用系统凭据管理器（credential helper），不靠 URL 内嵌 token。

### 修复

```bash
git remote set-url origin https://github.com/<用户>/<仓库>.git
```

### 预防

- [ ] 检查 `git remote -v`：应为纯 https 无 token
- [ ] 已泄露的 token **立即吊销**（GitHub Settings → Developer settings → Personal access tokens）
- [ ] 认证靠凭据管理器：`git config --global credential.helper manager`

## 事故 8：插件开发契约 —— 客户端/服务端插件 API 易错点

**根因类型**：⚠️ **框架契约违反**

### 服务端插件（lib/index.js）

| 错误 | 根因 | 修复 |
|---|---|---|
| `cannot get property "webServer" without inject` | cordis ctx 是代理，未声明属性直接抛错 | `ctx.inject(['webServer'], (scope) => { scope.webServer ... })` |
| `xxx is not defined` (500) | 函数定义在引擎闭包外 | 移入引擎内部，用 `engine.xxx` 暴露 |
| `Cannot access 'xxx' before initialization` | 变量名与函数名同名（TDZ 遮蔽） | 局部变量改名 |

### 客户端插件（lib/client.js）

| 错误 | 根因 | 修复 |
|---|---|---|
| `ctx is not defined` | client 插件必须导出 `exports.apply(ctx)` | loader 通过 apply 注入 ctx，不能顶层直接调用 |
| 卡片不显示 | client 端必须用**顶层** `exports.inject = ['slots']` | scoped `ctx.inject` 在 client 端不生效 |
| `window.React` undefined | 浏览器无全局 React | `require('react')`（模块加载器提供） |

### 其他开发期坑

- **时间戳**：Windows 文件名禁止 `:`；`new Date('无冒号串')` 是 Invalid Date，`getFullYear()` 静默返回 NaN → 用规范格式 + `isNaN` 容错
- **bat 中文注释**：cmd 解析中文 `rem` 行崩溃 → 英文注释 + GBK 编码

### 预防

- [ ] 客户端：`exports.apply(ctx)` + 顶层 `exports.inject`
- [ ] 服务端：`ctx.inject(['webServer'], ...)` 取服务
- [ ] 文件名时间戳无冒号；日期解析加 NaN 容错

- [ ] **三处一致性**：git 仓库 / npm 包 / 本地安装目录，代码哈希一致
- [ ] **语法检查**：`node --check lib/index.js` 和 `node --check lib/client.js`

## 事故 17：会话历史加载失败 —— 双实例并发写同一会话日志（seq gap 损坏）

**根因类型**：⚠️ **数据文件损坏（并发写）**

### 症状

- GUI 报：`history unavailable for session "session-xxx": Error: corrupt session log: seq gap in committed region at line N (expected X, got Y)（internal）`
- 该会话历史无法加载

### 根因（关键知识点）

- 会话日志 `session.jsonl.zstd` 是 **zstd 多帧 JSONL**，追加式写入，要求事件 seq **严格连续 0..N**
- **两个 dsh 实例共享同一数据目录、同时打开同一会话并各自追加** → 尾部出现同 seq 事件的交叉帧（常见触发：主实例崩溃/关闭后用备用实例——不同端口或 profile——继续同一会话）
- 加载器扫描到第二个写者从旧 seq 追加的事件 → `expected X, got Y` → 视为损坏直接抛错
- **该后端只自动修复"撕裂帧"（torn frame），不修复 seq gap** → 需手动重建
- 两个实例的内容可能**分叉**（同 seq 不同事件：一个实例中断了工具调用，另一个跑完并继续对话），形成两条交叉时间线，不是简单重复

### 排查

1. 确认是否双实例：查看监听端口的进程命令行（`web` 与 `--profile fallback --port <端口>` 并存 = 双写风险）
2. 确认无进程在写该文件：`LastWriteTime` 稳定 + 独占打开测试（`FileShare.None` 不抛共享冲突 = 无占用）
3. 定位损坏点：复刻后端 `scanZstdFrames` + 事件扫描逻辑（逐帧 `zstdDecompressSync` → 逐行解析 → 展开 packed rows：`text-chunks`/`reasoning-chunks`/`tool-call-chunks` 按 `seq0` + 成员数展开），找第一个 `seq != expected` 的事件及所在帧

### 修复（无损重建）

1. **先备份**原文件
2. 逐帧解码全部事件，从第一个坏帧起按 seq 去重：`seq == expected` 保留，`seq < expected` 跳过（重复），`seq > expected` 是真空洞（无法恢复）
3. 坏帧之前的字节**原样保留**（含 header 帧，保证第一帧恰为一行 header），去重事件序列化为 JSONL，用 `zstdCompressSync(input, { params: { checksumFlag: 1 } })` 压成新帧接在后面；**逐帧处理，绝不整体解压整体压缩**（见事故 0）
4. 重扫验证：seq 连续 0..N、无 gap、无 torn
5. 刷新 GUI 重新打开会话即恢复（无需重启 dsh）

### 注意

- **"保留首次出现"在时间线分叉时会得到混合时间线**（尾部可能错乱：缺用户消息、孤立推理块）——用户接受"可用即可"时即为最终方案；要更精确需按时间戳/连贯性挑选一条完整分支并重排 seq
- 双实例下改文件前必须确认无进程在写，否则越修越坏

### 预防

- [ ] **同一数据目录只允许一个 dsh 实例**；用备用实例继续旧会话前先确认旧实例已死（端口已释放）
- [ ] 不要同时在两个 GUI 打开同一会话
- [ ] 出现"历史加载失败 + seq gap"先查是否双实例在跑
- [ ] 长会话定期开新会话（>1000 步），降低恢复代价
