> 供 dsh-ops 技能引用。含个人细节的完整版仅保存在使用者本地。

## 事故 0：dsh 崩溃 —— zstd 会话文件被错误合并成单帧

**根因类型**：⚠️ **数据文件格式被破坏**

### 症状

- dsh 无法启动，报 `corrupt Zstandard session log: first frame is not exactly one header line`

### 根因（关键知识点）

- dsh 会话文件（`session.jsonl.zstd`）是 **zstd 多帧 JSONL**：每个 JSON 对象一个独立 zstd 帧
- **第一帧必须是恰好一行 header**（`assertZstdHeaderFrame` 校验）
- 用"整体解压 → 整体压缩"会合并成单帧 = **损坏**
- 正确修复：**逐帧处理**，保留帧边界

### 预防

- [ ] **绝不**用整体解压/整体压缩改写 dsh 会话文件
- [ ] 处理 zstd 会话必须逐帧操作
- [ ] 改 dsh 数据前先备份

## 事故 1：插件包名从裸名改为作用域包后漏改 3 处引用

**根因类型**：⚠️ **改名/改结构时旧名残留**（最高频事故类型）

### 症状

- 启动报 `Cannot find package '<旧包名>'`（服务端）
- 浏览器报 `loaded without registering "@<新包名>"`（客户端）

### 根因（关键知识点）

包名是**三层系统**，改名时三层都要同步：

| 层 | 文件 | 字段 | 作用 |
|---|---|---|---|
| ① 依赖声明 | `package.json` | `name` | npm 包身份 |
| ② 服务端挂载 | `cordis.patch.yml` | `name` | loader 按**包名** import |
| ③ 客户端模块 | `lib/client.js` | `__ModuleLoader__.load({ id })` | 浏览器端注册名 |

**可保留短名的地方**（对照 modlens 官方模式）：
- `lib/index.js` 的 `export const name`（cordis 注册 id）
- slots 注册的 `id`（界面条目 id）
- HTTP 路由前缀

### 预防

- [ ] 改名后全局搜索旧包名（含 `.yml` 和 `.js`）
- [ ] 对照 modlens：**patch name / client id = 完整包名，代码内注册名 = 短名**

## 事故 2：npm 发布后 registry 查询 404（CDN 传播延迟）

**症状**：发布命令成功但 `npm view` / registry API 404
**根因**：npm registry 的**写入节点与读取节点（CDN 边缘）传播有延迟**

### 判断发布是否成功（三连验证）

1. **重复发布**：再跑 `npm publish --access public` → 报 `You cannot publish over the previously published versions: X.Y.Z` = **包确实已发布**
2. **jsDelivr 交叉验证**：`https://cdn.jsdelivr.net/npm/<包>@<版本>/package.json` → HTTP 200
3. **等待后重查**：`npm view` 通常几分钟内恢复

### 预防

- [ ] 发布后不要立刻用 `npm view` 判断成败
- [ ] 发布命令 exit=0 + 无报错 = 已成功

## 事故 6：隐私保护 —— 含本机信息的文件绝不发布到公开仓库

**根因**：开发期文档天然包含本机细节（绝对路径、用户目录、token、数据目录），直接复制进公开仓库即泄露

### 铁律

> **发布到公开仓库（GitHub/npm）的任何文件，绝不包含：本机路径、用户名、token、API key、数据目录结构。**

### 判断标准（发布前扫描）

| 模式 | 示例 | 处理 |
|---|---|---|
| 盘符绝对路径 | `D:\Program Files\...` | 占位符 `<安装目录>` 或删掉 |
| 用户目录 | `C:\Users\<用户名>\...` | 改为 `~` 或删除 |
| token | `ghp_xxx` / `npm_xxx` | 绝不出现（用 `<token>` 代替） |
| 数据目录 | `...\dsh-data\profiles\...` | 用 `$DSH_HOME/...` 表示 |

### 正确做法（双文件模式）

| 文件 | 用途 | 内容 |
|---|---|---|
| **本地完整版** | 自己看，含全部路径细节 | 完整保留 |
| **发布公开版** | 给别人看，零隐私 | 路径用占位符，规则通用化 |

### 编码陷阱

用 PowerShell `Set-Content -Encoding UTF8` 写中文文件会得到 **UTF-8 with BOM 且内容被 GBK 误解**，导致技能解析失败（乱码）。写中文文件必须用 write 工具（正确 UTF-8 无 BOM）。

## 事故 7：GitHub token 泄露 —— token 曾写入 remote URL

**根因类型**：⚠️ **凭据泄露**

### 根因

早期推送时把 token 拼进 remote URL（`https://user:token@github.com/...`）绕开认证。该 URL 会被 git 记录、也可能被日志/截图泄露。

### 铁律

> **token 绝不写入 git remote URL、绝不写进代码/配置文件、绝不在对话中明文贴出。**
> 认证用系统凭据管理器（credential helper），不靠 URL 内嵌 token。

### 修复

```bash
git remote set-url origin https://github.com/<用户>/<仓库>.git
```

### 预防

- [ ] 检查 `git remote -v`：应为纯 https 无 token
- [ ] 已泄露的 token **立即吊销**（GitHub Settings → Developer settings → Personal access tokens）
- [ ] 认证靠凭据管理器：`git config --global credential.helper manager`

## 事故 8：插件开发契约 —— 客户端/服务端插件 API 易错点

**根因类型**：⚠️ **框架契约违反**

### 服务端插件（lib/index.js）

| 错误 | 根因 | 修复 |
|---|---|---|
| `cannot get property "webServer" without inject` | cordis ctx 是代理，未声明属性直接抛错 | `ctx.inject(['webServer'], (scope) => { scope.webServer ... })` |
| `xxx is not defined` (500) | 函数定义在引擎闭包外 | 移入引擎内部，用 `engine.xxx` 暴露 |
| `Cannot access 'xxx' before initialization` | 变量名与函数名同名（TDZ 遮蔽） | 局部变量改名 |

### 客户端插件（lib/client.js）

| 错误 | 根因 | 修复 |
|---|---|---|
| `ctx is not defined` | client 插件必须导出 `exports.apply(ctx)` | loader 通过 apply 注入 ctx，不能顶层直接调用 |
| 卡片不显示 | client 端必须用**顶层** `exports.inject = ['slots']` | scoped `ctx.inject` 在 client 端不生效 |
| `window.React` undefined | 浏览器无全局 React | `require('react')`（模块加载器提供） |

### 其他开发期坑

- **时间戳**：Windows 文件名禁止 `:`；`new Date('无冒号串')` 是 Invalid Date，`getFullYear()` 静默返回 NaN → 用规范格式 + `isNaN` 容错
- **bat 中文注释**：cmd 解析中文 `rem` 行崩溃 → 英文注释 + GBK 编码

### 预防

- [ ] 客户端：`exports.apply(ctx)` + 顶层 `exports.inject`
- [ ] 服务端：`ctx.inject(['webServer'], ...)` 取服务
- [ ] 文件名时间戳无冒号；日期解析加 NaN 容错

## 事故 9：GitHub API 未认证限流 —— 60 次/小时 vs 5000 次/小时

**症状**：查询仓库星数、issues 时连续 403 `已禁止`，一度以为网络/仓库问题
**根因**：GitHub API（api.github.com）**未认证请求限流 60 次/小时/IP**；**带 token 认证后 5000 次/小时**

### 修复方法

从系统凭据管理器取 GitHub token，请求头带 `Authorization`（不落盘、不进 URL）：

```powershell
# 1. 取 token（git credential 经 cmd 管道）
$tempFile = Join-Path $env:TEMP "gh-cred-in.txt"
$outFile = Join-Path $env:TEMP "gh-cred-out.txt"
Set-Content -Path $tempFile -Value "protocol=https`nhost=github.com`n" -NoNewline
cmd /c "`"$git`" credential fill < `"$tempFile`" > `"$outFile`" 2>&1"
$cred = Get-Content $outFile -Raw
$token = ($cred -split "`n" | Where-Object { $_ -like 'password=*' } | Select-Object -First 1).Replace('password=', '')

# 2. 带认证查询
$headers = @{ 'Authorization' = "token $token"; 'User-Agent' = 'dsh-review' }
Invoke-RestMethod -Uri 'https://api.github.com/repos/<某仓库>' -Headers $headers

# 3. 查额度
Invoke-RestMethod -Uri 'https://api.github.com/rate_limit' -Headers $headers
```

### 预防

- [ ] 查询 GitHub API **一律带 token**（5000 次/小时），不要用匿名（60 次/小时）
- [ ] token 从凭据管理器获取，**不写进脚本文件**、不打印、不进 URL

## 事故 10：插件配置页卡片不显示 —— 必须注册 settings namespace

**根因类型**：⚠️ **框架契约违反**

**症状**：插件改 key、改箭头函数后卡片仍不显示在「插件 → 插件配置」页

**根因（关键机制）**：插件配置页只渲染"注册了 settings namespace"的插件的卡片：
```js
const { namespaces } = props.useConfigurablePlugins(...)  // 枚举配置命名空间
namespaces.map((ns) => renderSlot("settings.plugin.item", {}, { entryKey: ns }))
```
不注册 namespace → 不在 namespaces 列表 → 卡片永远不会被 `renderSlot` 调用。

### 修复

```js
import { installSettingsSection, settingsNamespace } from '@deepseek-ai/dsh-settings'
import z from '@deepseek-ai/schemastery'
installSettingsSection(ctx, settingsNamespace('<插件名>'), z.object({}), {}, { setSource: () => {}, onChange: () => {} })
```
schema 必须是 **schemastery** 的（`z.object`），不是纯 JSON 对象。

**卡片外壳**（`<li>` + 标题 + 折叠）由插件自己实现（dsh-restart 的 SettingsCard 自带），需自己加。

## 事故 11：PowerShell 窗口反复弹出 —— 无控制台进程的子进程弹窗

**根因类型**：⚠️ **进程管理**

**根因（进程父链证实）**：
1. 重启类插件用 `spawn(execPath, argv, { detached: true })` 重启 dsh
2. **Windows 上 `detached:true` = DETACHED_PROCESS** → 新 dsh **无控制台**
3. 无控制台的进程 spawn 控制台子进程 → **每个子进程各自弹可见窗口**
4. 用 `powershell -WindowStyle Hidden` 包装的旧方案 → dsh 有隐藏控制台 → 不弹，但包装会导致重启失败

### 正确修复

**`spawn(execPath, argv, { detached: true, windowsHide: true })`** —— detached 保持重启成功，windowsHide 隐藏子进程窗口。

> ⚠️ 重启 helper **不能用 `powershell -WindowStyle Hidden` 包装**（会重启失败、日志空）。正确组合是 `detached + windowsHide`。

## 事故 14：pnpm 重装覆盖插件补丁 + PS 脚本编码破坏 UTF-8 文件

**根因类型**：⚠️ **构建/安装副作用** + ⚠️ **编码陷阱**

**时间线**：
1. 两个插件合并为自持插件（本地仓库开发，`file:` 来源安装）
2. `pnpm install` 重写整个 node_modules → **手动补丁全被覆盖**
3. 补丁脚本用 `Get-Content`（ANSI 解码）+ `Set-Content`（UTF8 写回）把源文件的中文模板字符串写坏（乱码 + 语法错误）
4. 从 npm 重新下载干净 tarball 恢复，修复脚本后重打补丁成功

### 关键知识点

- **市场一键更新 = `pnpm add <name>@latest` 重装整个包目录**，node_modules 手动修改全部丢失
- 市场对 `link:` / `file:` 来源的插件**拒绝更新** → 自持插件用 `file:` 或 `github:` 安装可永久保护
- private 包（npm 上只有旧版本）`pnpm install` 会报 `ERR_PNPM_NO_MATCHING_VERSION`
- pnpm store 位置不匹配时（`.modules.yaml` 记录旧 store），需要 `CI=true pnpm install --no-frozen-lockfile` 重建
- **PowerShell 5.1 处理 UTF-8 无 BOM 文件**：`Get-Content` 按 ANSI 解码、`Set-Content -Encoding UTF8` 写回 → **中文必乱**。正确：`[System.IO.File]::ReadAllText()` / `WriteAllText(path, content, UTF8Encoding($false))`
- **PS 5.1 执行 UTF-8 无 BOM 的 .ps1 本身**也会中文乱码解析失败 → 脚本文件必须存 UTF-8 **带 BOM**
- 补丁重放脚本要**幂等**（检测已打则跳过），文件读写必须字节安全

### 预防

- [ ] 自持插件（有本地补丁的）一律用 `file:` 或 `github:` 安装，禁用市场一键更新
- [ ] 市场更新前先看哪些插件有补丁，更新后立刻重跑补丁脚本
- [ ] 修改 node_modules 的脚本：读写用 `[System.IO.File]`，.ps1 存 UTF-8 BOM

## 事故 15：pnpm install 清空官方 bundle → 启动失败（Failed to load plugins）

**根因类型**：⚠️ **构建/安装副作用**

**症状**：主进程启动失败，报 `failed to import loader entry (...): client-modules: bundle script ... failed to load`；`node_modules/@deepseek-ai/*` 官方 bundle 被清空

**根因**：profile 的 `package.json` 结构不正规——`dsh.profile.bundles` 里声明了官方 bundle，但 `dependencies` 里没有 → 执行 `pnpm install` 时按 dependencies + lock 重建 node_modules → 未声明的官方 bundle 全被清 → 启动找不到 bundle

### 修复

1. `package.json` 的 `dependencies` 补上官方 bundle（参照 fallback profile 的版本范围）
2. `pnpm install --no-frozen-lockfile`（CI=true）重装
3. 重打被覆盖的补丁（`reapply-patches.ps1`）
4. allowBuilds 警告（koffi/node-pty 等构建被忽略）**可忽略**：fallback 未 approve 也工作正常

### 关键知识点

- profile 的 package.json **必须把官方 bundle 写进 dependencies**，否则任何 `pnpm install` 都会清空它们
- `pnpm install` 是**重建式**操作：按 lock+dependencies 重组 node_modules，**所有不在 dependencies 里的手动包/补丁都会被清**
- 市场一键更新（`pnpm add`）也会触发同类重建 → 更新后必须跑补丁脚本

### 预防

- [ ] 修改 profile 的 package.json 依赖后**先备份**（存 `web-package.json.reference`）
- [ ] 任何 pnpm install 后：①查官方 bundle 是否还在 ②跑补丁脚本重打补丁
- [ ] 用 `--no-frozen-lockfile` 前先确认 lock 已含全部所需依赖

## 事故 16：视觉方案排查全记录（插件合并 + 视觉路由冲突 + 会话过长）

**根因类型**：⚠️ **插件冲突** + ⚠️ **性能**

### 一、插件合并

- 合并余额卡 + 重启/停止为自持插件，三层同步：`package.json name` = `cordis.patch.yml name` = `client.js load id`
- **关键坑**：settings 卡片注册 `settings.plugin.item` 时，**hooks key 不能带 `use` 前缀**（框架自动从 `dshDock` 铸出 `props.useDshDock`；写 `useDshDock` 会报 `props.useDshDock is not a function`）
- 设置卡片命名空间：服务端 `settingsNamespace(...)` = 客户端 bind namespace = 卡片 key，三处一致
- **npm 发布后 pnpm 装不上**：dist-tags 为空或 CDN 延迟 → `npm dist-tag add <pkg>@<ver> latest`
- **pnpm 24h 冷静期**：新发布版本 `add @latest` 被拦 → `--config.minimumReleaseAge=0` 绕过

### 二、视觉路由插件冲突（重要）

- 免费视觉链（匿名端点，限流约 2 次/分/IP）与视觉变体插件冲突：
  - `stealth: true`（默认）让路由插件**接管默认模型路由** → 所有文本请求经过包装层 → **整体变慢**
  - 免费链不稳定：超时 / 400（请求体超限）/ 限流
- **结论**：两个视觉方案**不能同时装**，保留一个，用传统模式

### 三、视觉变体两种模式

- **传统模式（推荐）**：粘贴图片自动转成文件路径 → 读图工具读图，**模型永远用普通模型**，不被锁
- **视觉变体**：原生缩略图，但**模型被锁死**（会话有图时禁止切纯文本模型），长会话更慢
- **教训**：变体"所见即所得"代价太大，日常用传统模式

### 四、响应慢的真正根因（不是插件）

- **会话过长**：上千步 / 数十 MB / 每轮约 10 万 token 上下文
- 任何模型在超长会话里都慢（首 token 与上下文长度成正比）→ **开新会话立即恢复速度**

### 五、备用方案

- 已下载安装 CLI 工具（校验通过、加入 PATH），但**区域不可用**（账号资格检查受区域限制，同 Gemini 情况）
- token 已存 keyring，但 eligibility 检查过不了

### 关键知识点

- 模型选择器锁死 = 会话里有图片附件（规则，**不是 bug**）；开新会话即解锁
- 视觉插件二选一，别同时装（抢路由）
- 长会话性能：10 万 token 上下文 → 首 token 慢是物理限制，开新会话

### 预防

- [ ] 视觉方案：用传统模式，模型保持默认
- [ ] 长会话定期开新会话（>1000 步就该换）
- [ ] 新插件安装前检查与现有插件是否冲突（尤其视觉类）

## 事故 17：会话历史加载失败 —— 双实例并发写同一会话日志（seq gap 损坏）

**根因类型**：⚠️ **数据文件损坏（并发写）**

### 症状

- GUI 报：`history unavailable for session "session-xxx": Error: corrupt session log: seq gap in committed region at line N (expected X, got Y)（internal）`
- 该会话历史无法加载

### 根因（关键知识点）

- 会话日志 `session.jsonl.zstd` 是 **zstd 多帧 JSONL**，追加式写入，要求事件 seq **严格连续 0..N**
- **两个 dsh 实例共享同一数据目录、同时打开同一会话并各自追加** → 尾部出现同 seq 事件的交叉帧（常见触发：主实例崩溃/关闭后用备用实例——不同端口或 profile——继续同一会话）
- 加载器扫描到第二个写者从旧 seq 追加的事件 → `expected X, got Y` → 视为损坏直接抛错
- **该后端只自动修复"撕裂帧"（torn frame），不修复 seq gap** → 需手动重建
- 两个实例的内容可能**分叉**（同 seq 不同事件：一个实例中断了工具调用，另一个跑完并继续对话），形成两条交叉时间线，不是简单重复

### 排查

1. 确认是否双实例：查看监听端口的进程命令行（`web` 与 `--profile fallback --port <端口>` 并存 = 双写风险）
2. 确认无进程在写该文件：`LastWriteTime` 稳定 + 独占打开测试（`FileShare.None` 不抛共享冲突 = 无占用）
3. 定位损坏点：复刻后端 `scanZstdFrames` + 事件扫描逻辑（逐帧 `zstdDecompressSync` → 逐行解析 → 展开 packed rows：`text-chunks`/`reasoning-chunks`/`tool-call-chunks` 按 `seq0` + 成员数展开），找第一个 `seq != expected` 的事件及所在帧

### 修复（无损重建）

1. **先备份**原文件
2. 逐帧解码全部事件，从第一个坏帧起按 seq 去重：`seq == expected` 保留，`seq < expected` 跳过（重复），`seq > expected` 是真空洞（无法恢复）
3. 坏帧之前的字节**原样保留**（含 header 帧，保证第一帧恰为一行 header），去重事件序列化为 JSONL，用 `zstdCompressSync(input, { params: { checksumFlag: 1 } })` 压成新帧接在后面；**逐帧处理，绝不整体解压整体压缩**（见事故 0）
4. 重扫验证：seq 连续 0..N、无 gap、无 torn
5. 刷新 GUI 重新打开会话即恢复（无需重启 dsh）

### 注意

- **"保留首次出现"在时间线分叉时会得到混合时间线**（尾部可能错乱：缺用户消息、孤立推理块）——用户接受"可用即可"时即为最终方案；要更精确需按时间戳/连贯性挑选一条完整分支并重排 seq
- 双实例下改文件前必须确认无进程在写，否则越修越坏

### 预防

- [ ] **同一数据目录只允许一个 dsh 实例**；用备用实例继续旧会话前先确认旧实例已死（端口已释放）
- [ ] 不要同时在两个 GUI 打开同一会话
- [ ] 出现"历史加载失败 + seq gap"先查是否双实例在跑
- [ ] 长会话定期开新会话（>1000 步），降低恢复代价
